# Ozon Seller API audit

Документ содержит карту используемых сервисом методов Ozon Seller API и заметки по контрактам. Реальные ответы кабинета остаются главным источником при проверке доступности, полей и лимитов.

## 1. Методы Ozon Seller API

Перечислены методы, которые вызывает текущий адаптер. Контракты нужно перепроверить по фактическому ответу кабинета при первом авторизованном подключении.

| Назначение | Реализованный метод | Какие данные используются | Ограничения и незавершённая проверка |
| --- | --- | --- | --- |
| Заказы FBO и статусы отправлений | `POST /v3/posting/fbo/list` | ID отправления/заказа и статус; у товаров `offer_id`, Ozon `sku`, количество, цена; `is_marketplace_buyout`; можно запросить финансовые данные | В официальном канале сообщалось, что `/v2/posting/fbo/list` отключат 2026-08-31, заменив на v3. В v3 используется курсорная пагинация, период запроса ограничен одним годом. |
| Возвраты, включая FBO | `POST /v1/returns/list` | ID, тип и схема возврата; ID заказа/отправления; артикул/SKU/количество товара; текущее и целевое место; отображаемый статус | В официальном канале этот метод указан как замена старых методов возврата компании для FBO/FBS. Статус API не доказывает, что продавец физически забрал возврат: склад продавца меняется только после подтверждения получения. 2026-10-15 в ответ метода добавили `courier_delivery`; схему нужно перепроверить. |
| Начисления за день | `POST /v1/finance/accrual/by-day` | Финансовые начисления и корректировки, необходимые для учёта выручки, комиссий и логистики; начисления компенсаций выделяются по типам Ozon `10` и `25` | В строках `ITEM` суммы сохраняются отдельно по `sku` и `type_id`, чтобы компенсация не смешивалась с логистикой и удержаниями. Компенсация признаётся по единственной финансовой строке; сумма из отчёта списаний не прибавляется повторно. Типы и связь нужно сверить на первом авторизованном ответе кабинета. |
| Выкуп товара маркетплейсом | `POST /v1/finance/products/buyout` | Отправление, артикул/SKU, количество, цена выкупа и сумма к начислению; FBO-товар также может иметь явный `is_marketplace_buyout` в заказе | В ответе выкупа есть `amount` (сумма к начислению), `buyout_price`, `posting_number`, SKU и количество, но нет даты отдельной строки. Не добавлять сумму отчёта поверх начислений, пока их связь не сверена на данных кабинета. Дата признания должна быть стабильной и не может подменяться датой 1970 или датой последующего складского пересчёта. |
| Продажи юридическим лицам | `POST /v1/finance/document-b2b-sales/json` | Реестр счетов и операций реализации/возврата; операция содержит дату, отправление, артикул/SKU, количество, цену, сумму и тип | Отдельный реестр финансовых документов, а не классификатор отрицательной строки продажи. В адаптер пока не включён: связь и возможное пересечение сумм с дневными начислениями нужно проверить на данных кабинета до учёта в балансе. |
| Списания Ozon и статус компенсации | `POST /v1/analytics/decommissioned-goods` | Отчёт о списанных товарах FBO: товар, количество, причина, тип/сумма компенсации | Строки сохраняются; сопоставленный товар с датой уменьшает остаток Ozon. Поля компенсации остаются для сверки; денежный эффект берётся из дневных финансовых начислений и учитывается один раз. Сверка живых данных кабинета ещё не выполнена. |

### 1.1. Известное расхождение в контракте и проверки живой интеграции

- В официальном сообщении Seller API от 2026-06-09 указано, что поле ответа `accruals.type_id` метода `/v1/finance/accrual/by-day` переименовано в `accruals.accrual_id`. Публичная копия OpenAPI всё ещё содержит `type_id`; адаптер сохраняет исходный ответ и читает новое имя с совместимостью для старого.
- API показывает текущее/целевое место и отображаемый статус возврата, но в ходе аудита не удалось установить API-событие, которое доказывает физическое получение товара владельцем. Оставить ручное подтверждение «получил» до тех пор, пока контракт и реальные ответы однозначно не подтвердят другое.
- При возврате на Ozon товар возвращается в остаток, только когда Ozon снова показывает его доступным к продаже. Точный статус/сигнал наличия и связь возврата с исходным отправлением нужно проверить на примерах до реализации складского эффекта.
- Проверить, что лента начислений содержит даты и суммы, нужные для расчётного баланса до выплаты Ozon, и позволяет идемпотентно получить последующие корректировки. Начисление нельзя считать фактической выплатой на банковский счёт.
- Код выделяет компенсационные начисления типов `10` и `25` из `/v1/finance/accrual/by-day`; для `ITEM` начисления разбиваются по типу. Проверить типы и сумму на реальных примерах кабинета. Пока связь конкретной строки списания с финансовой строкой не подтверждена, отчётную сумму не использовать как самостоятельный денежный источник.
- Проверить доступность методов и глубину истории по фактическим результатам синхронизации: успешный ответ одного метода не подтверждает доступность остальных.
- Версии методов, поля и лимиты API могут измениться; проверить их вместе с правами доступа и примерами ответов при подключении кабинета.
